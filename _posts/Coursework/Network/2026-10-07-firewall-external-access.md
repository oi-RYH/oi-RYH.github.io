친구가 집 주소와 주문 창구 번호를 정확히 알고 있어도, 성벽이나 현관의 경비가 막으면 도착하지 못한다. 네트워크에서도 **주소가 맞는 것과 통신이 허용되는 것은 별개**다.

이번 영상은 경비 골렘을 방화벽에 비유하고, 외부에서 서비스에 접근하는 세 방법을 비교한다. 포트 포워딩과 터널은 집으로 들어오는 길을 만들고, 클라우드 배포는 주문을 처리하는 장소 자체를 옮긴다.

## 경로에 적용되는 방화벽

방화벽은 규칙에 따라 통신을 허용하거나 차단한다. AWS EC2 같은 클라우드 가상 서버에서는 보안 그룹과 운영체제의 호스트 방화벽이 함께 적용될 수 있다.

- 성벽의 골렘: 클라우드 자원에 적용되는 보안 그룹
- 현관의 골렘: Windows 방화벽이나 Linux의 ufw 등 호스트 쪽 설정

영상의 두 경비는 여러 계층을 함께 확인하라는 비유다. 모든 환경에 항상 정확히 두 개의 방화벽이 있다는 뜻은 아니다. 서비스가 실행 중인지, 올바른 주소와 포트에 bind했는지도 확인해야 한다.

## 보안 그룹은 통신 허용 규칙의 묶음

AWS의 **Security Group**, 즉 보안 그룹은 연결된 자원에 어떤 통신을 허용할지 정하는 규칙 묶음이다. 인바운드와 아웃바운드 규칙을 구분하며, 허용 규칙을 추가하는 방식으로 동작한다. [AWS 보안 그룹 설명](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html)

웹 서버에 다음 인바운드 규칙만 적용했다고 하자.

| 프로토콜과 포트 | 출발지 | 허용 규칙 | 새로 들어오는 연결 |
|---|---|---|---|
| TCP 443 | 0.0.0.0/0 | 있음 | 해당 규칙으로 허용 |
| TCP 22 | 해당 항목 없음 | 없음 | 다른 허용 규칙도 없다면 차단 |

`0.0.0.0/0`은 모든 IPv4 출발지를 뜻한다. IPv6는 별도 범위와 규칙을 확인해야 한다. 443은 HTTPS에서 흔히 쓰는 포트이고, 22는 SSH 원격 관리에 흔히 쓰인다.

여기서 “22번 규칙 없음”은 거부 규칙을 써 놓았다는 뜻이 아니다. **허용하는 규칙이 없으므로 새 인바운드 연결이 허용되지 않는 것**이다. 여러 보안 그룹을 연결했다면 그 규칙들이 합쳐져 적용되므로 한 그룹만 보고 판단하면 안 된다.

보안 그룹은 상태 저장 방식으로 동작해 허용한 통신의 응답도 추적한다. 반면 모든 방화벽 제품이 똑같은 규칙 체계를 쓰는 것은 아니다.

## 포트 포워딩

포트 포워딩은 밖의 특정 주소·포트로 온 통신을 정해 둔 내부 주소·포트로 전달하는 설정이다.

```text
외부 친구
  → 공유기의 공인 주소:8080
  → 192.168.0.23:8000
  → 내 PC의 주문 프로그램
```

이 경우 프로그램은 여전히 내 PC에서 실행된다. 외부에서 도달할 수 있는 공인 주소, 공유기 설정 권한, 내부 서버의 안정적인 주소, 필요한 방화벽 허용이 있어야 한다.

상위 통신사 장비가 NAT를 하는 CGNAT 환경이나 이중 NAT 환경에서는 집 공유기에 규칙 하나를 추가하는 것만으로 부족할 수 있다. 외부 포트를 바꾼다고 인증·업데이트 같은 보안 대책이 대체되지는 않는다.

## 역방향 터널의 방향

일반적인 직접 접속은 친구가 바깥에서 집 서버를 향해 연결을 시작한다. **역방향 터널은 집 쪽 프로그램이 먼저 바깥 중계소에 연결한다.** 반대인 것은 연결을 시작하는 방향이지, 데이터가 한쪽으로만 흐른다는 뜻이 아니다.

```text
터널 준비: 내 PC → 바깥 중계소
친구 요청: 친구 → 중계소 → 유지된 터널 → 내 PC
서버 응답: 내 PC → 유지된 터널 → 중계소 → 친구
```

Cloudflare Tunnel은 서버 쪽의 `cloudflared`가 밖으로 연결을 만드는 방식이다. 이런 구성은 보통 집 공유기의 인바운드 포트 포워딩 없이 서비스에 접근할 경로를 만들 수 있다. 나가는 연결과 터널 사용 자체는 허용돼야 한다. [Cloudflare Tunnel 문서](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)

ngrok이나 SSH의 원격 포트 포워딩도 비슷한 문제를 해결할 때 쓰인다. 주소가 임시인지 고정인지, 공개 범위와 인증을 어떻게 설정하는지는 서비스와 구성에 따라 다르다. **터널의 공개 URL을 만들었다는 것만으로 접근 인증까지 마련되는 것은 아니다.**

## 클라우드 배포는 실행 장소 변경

클라우드 배포는 집으로 들어오는 길만 여는 것이 아니라 프로그램과 필요한 설정·데이터를 클라우드 환경으로 옮겨 그곳에서 실행하는 방식이다.

| 방법 | 프로그램 실행 위치 | 외부 요청이 들어오는 방식 |
|---|---|---|
| 포트 포워딩 | 내 PC | 공유기가 내부 주소·포트로 전달 |
| 역방향 터널 | 내 PC | 중계소가 미리 열린 터널로 전달 |
| 클라우드 배포 | 클라우드 | 클라우드에서 요청을 받아 처리 |

앞의 두 방법은 내 PC나 프로그램을 끄면 요청을 처리할 수 없다. 클라우드 배포는 집 PC에 의존하는 부분까지 옮겼다면 내 PC가 꺼져도 동작할 수 있다. 데이터베이스는 집에 남겨 놓은 채 앱만 옮겼다면 그 의존성은 여전히 남는다.

EC2처럼 가상 서버를 쓰는 경우와 Cloud Run 같은 관리형 실행 환경은 관리 책임이 다르다. 배포 후에도 비용, 접근 범위, 인증, 비밀 정보 관리와 서비스 운영을 확인해야 한다.

## 권한과 공개 범위

학교나 회사 네트워크에서는 관리자 정책과 승인된 사용 범위를 먼저 확인한다. 공유기 설정 권한이 없다고 터널로 차단 정책을 우회해도 된다는 뜻은 아니다.

어떤 방법이든 **서비스 실행·bind, 주소, 경로, 통신 허용**을 함께 확인하고 공개 범위는 필요한 대상으로 줄인다.

## 핵심 정리

- 주소가 정확해도 방화벽이나 서비스 설정 때문에 접속하지 못할 수 있다.
- 보안 그룹은 실제 적용된 허용 규칙들을 함께 확인한다.
- 역방향 터널은 내부에서 외부로 연결을 먼저 시작한다.
- 클라우드 배포는 접근 경로뿐 아니라 프로그램 실행 장소도 바꾸는 방법이다.
