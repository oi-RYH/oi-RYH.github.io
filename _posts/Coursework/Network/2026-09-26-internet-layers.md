빵집까지 길을 연결했으니 주문서만 보내면 끝일까? 받는 쪽이 주문 형식을 이해해야 하고, 주문을 처리할 프로그램으로 전달해야 하며, 실제 연결을 통해 데이터를 보내야 한다.

이 일을 하나의 거대한 기능으로 생각하면 어디서 문제가 생겼는지 구분하기 어렵다. 관련된 기능을 묶어 역할별로 나눈 것이 **계층(Layer)**이다.

## 다섯 계층으로 나누어 보기

이 글은 물리 계층을 별도로 구분한 **인터넷 5계층 모델**을 사용한다. TCP/IP를 4계층으로 설명하는 자료에서는 물리 기능을 링크 계층과 함께 묶기도 한다. 이름의 개수보다 역할을 이해하는 것이 중요하다. 인터넷 프로토콜 계층의 기본 구분은 [RFC 1122 §1.1.3](https://www.rfc-editor.org/rfc/rfc1122.html#section-1.1.3)에서도 확인할 수 있다.

| 계층 | 빵 주문에서의 질문 | 주요 역할과 예 |
|---|---|---|
| 응용(Application) | 주문을 어떤 형식으로 주고받을까? | 메시지의 형식·의미·절차, HTTP·DNS·MQTT |
| 전송(Transport) | 양 끝의 어느 프로그램 사이 통신일까? | 응용 간 전달, TCP·UDP |
| 네트워크(Network) | 목적지까지 어떻게 전달할까? | IP 주소와 네트워크 간 패킷 전달 |
| 링크(Link) | 연결된 이 구간을 어떻게 건널까? | 같은 링크의 프레임 전달, 이더넷·Wi-Fi의 링크 기능 |
| 물리(Physical) | 비트를 어떻게 실제로 보낼까? | 전기·빛·전파를 이용한 신호 전달 |

이 다섯 계층은 주문서가 방문해야 하는 다섯 건물이 아니다. **한 장치의 통신 기능을 역할별로 설명하는 관점**이다. 또 이더넷과 Wi-Fi 같은 기술은 링크 기능뿐 아니라 물리 신호에 관한 규격도 포함하므로, 기술 하나가 항상 계층 하나에만 딱 들어맞는 것은 아니다.

## 응용 계층과 프로토콜

빵집이 “상품 이름과 수량을 보내 주세요”라고 약속했다고 하자. 보내는 쪽이 수량 자리에 주소를 적으면, 데이터가 도착해도 주문을 제대로 처리하기 어렵다.

통신 당사자가 따르는 규칙을 **프로토콜(Protocol)**이라고 한다. 메시지의 형식과 의미, 어떤 순서로 주고받는지 등의 약속이 포함된다. 프로토콜은 응용 계층에만 있는 것이 아니라 다른 계층에도 있다.

여기서 **API(Application Programming Interface)**도 구별해 두면 좋다. API는 프로그램이 다른 기능을 이용하는 접점과 사용 규칙이다. 모든 API가 네트워크를 사용하는 것은 아니지만, 웹 API라면 HTTP 같은 프로토콜 위에서 주문 접수 기능을 제공할 수 있다. 주문 API가 제공하는 기능과 HTTP라는 통신 규칙은 같은 개념이 아니다.

## 전송 계층과 네트워크 계층

같은 빵집 컴퓨터에서 주문 접수와 재고 관리 프로그램을 실행할 수 있다. 목적지 컴퓨터 쪽까지 도달하는 문제와, 그 안의 올바른 통신 접점으로 전달하는 문제는 구별된다.

전송 계층은 양 끝의 응용 프로그램 사이 통신을 제공한다. TCP·UDP에서 포트 번호는 통신 접점을 구분하는 데 쓰인다. 다만 포트 번호를 영구적인 프로그램 고유 번호라고 이해하면 안 된다.

TCP와 UDP는 제공하는 기능도 다르다. TCP는 순서 있는 신뢰성 있는 바이트 스트림을 제공하고, UDP 자체는 데이터그램의 도착·순서·재전송을 보장하지 않는다. 이것이 곧 모든 상황에서 UDP가 빠르고 TCP가 느리다는 뜻은 아니다. 필요한 기능과 실제 사용 방식을 함께 봐야 한다.

네트워크 계층은 IP 주소와 경로 정보를 이용해 네트워크 사이로 패킷을 전달하는 역할이다. 앞에서 본 라우터의 다음 홉 전달이 이 부분과 연결된다.

## 링크 계층과 물리 계층

먼 목적지로 가는 길도 개별 연결 구간들을 차례로 지난다. 영상의 레일과 수레는 한 구간을 건너는 링크 전달의 비유다.

하지만 실제로 종이 주문서나 수레가 케이블 안으로 들어가지는 않는다. 데이터의 비트가 전기 신호, 빛, 전파 등으로 표현되어 전달된다. 이것이 물리 계층에서 다루는 일이다.

**경로 전체의 전달, 한 링크의 전달, 실제 신호 전달은 서로 관련되지만 같은 질문이 아니다.**

## 캡슐화와 역캡슐화

보내는 쪽에서는 응용 데이터를 하위 계층으로 넘기며 전달에 필요한 정보를 붙인다. TCP/IP와 이더넷을 사용하는 한 예를 단순화하면 다음과 같다.

1. 응용 프로그램이 주문 메시지를 만든다.
2. TCP가 전송에 필요한 헤더를 붙여 세그먼트를 구성한다.
3. IP가 주소 등 정보를 붙여 패킷을 구성한다.
4. 링크 계층이 해당 링크의 프레임으로 담는다.
5. 물리 계층이 비트를 신호로 전달한다.

이처럼 상위 계층의 데이터를 하위 계층의 전송 단위에 담는 것을 **캡슐화(Encapsulation)**라고 한다. 받는 쪽에서는 각 계층의 정보를 해석하고 상위 계층으로 내용을 넘긴다. 이를 **역캡슐화(Decapsulation)**라고 한다.

물리 계층에서 포장 상자를 하나 더 씌우는 것으로 생각하지는 말자. 이 단계의 핵심은 신호 전달이다. 또한 실제로는 데이터를 나누거나 합치는 일이 있어 응용 메시지 하나와 패킷 하나가 반드시 일대일로 대응하지 않는다.

중간 라우터가 매번 빵 주문의 내용까지 읽고 응용 계층에 올리는 것도 아니다. 일반적인 IP 전달에서는 수신한 링크 정보를 처리하고 IP 정보를 확인한 뒤, 다음 링크에 맞는 프레임으로 다시 내보낸다.

## 호스트·서비스·엔드포인트

계층과 함께 용어의 관점도 구분해 보자.

| 용어 | 의미 | 주문 서비스의 예 |
|---|---|---|
| 호스트(Host) | 네트워크에 참여하는 컴퓨팅 시스템 | 주문 프로그램을 실행하는 PC나 가상 머신 |
| 서버(Server) | 서비스를 제공하는 역할 또는 그 프로그램 | 주문 요청을 처리하는 프로그램 |
| 서비스(Service) | 제공하는 기능 | 빵 주문 접수 |
| 엔드포인트(Endpoint) | 통신하거나 서비스에 접근하는 구체적 지점 | 주문 API의 접속 주소 |

엔드포인트가 항상 IP 하나만을 뜻하지는 않는다. 전송 계층 문맥에서는 IP 주소와 포트로 설명할 수 있고, 웹 API 문맥에서는 URL의 경로까지 포함해 말하기도 한다.

예를 들어 `https://api.example.com:443/orders`는 HTTPS 방식, 호스트 이름, 포트 443, `/orders` 경로를 담고 있다. 실제 API 동작을 구분할 때는 GET·POST 같은 HTTP 메서드도 함께 볼 수 있다. 엔드포인트라는 단어가 등장한 문맥을 확인하는 것이 중요하다.

## 계층을 나누는 이유

주문에 실패했을 때 “네트워크가 안 된다”라고만 말하면 범위가 너무 넓다. 신호·연결, 주소·경로, 통신 접점, 메시지 형식을 구분하면 무엇을 확인할지 정하기 쉬워진다.

다만 한 증상이 원인 계층 하나를 곧바로 증명하지는 않는다. 응답이 없다는 현상은 연결 문제일 수도 있고 서버 프로그램의 문제일 수도 있다. 계층은 원인을 좁히는 사고 도구다.

## 핵심 정리

- 계층은 통신 기능을 역할별로 나누는 관점이다.
- 보내는 쪽은 필요한 정보를 붙이고, 받는 쪽은 해석하며 상위 계층으로 넘긴다.
- 호스트·서버·서비스·엔드포인트는 장치, 역할, 기능, 접점을 구분하는 용어다.
